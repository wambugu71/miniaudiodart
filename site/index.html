Introduction

Most music players just hand your audio over to the operating system's shared mixer and let it do whatever it wants — which usually means coarse resampling, forced compression, and unwanted sound modifications. Sautiplay was built to avoid all of that.

At its heart is Sautiflow, a custom low-latency C++ audio engine. Instead of relying on high-level system wrappers, Sautiplay talks directly to low-level hardware paths like AAudio MMAP on Android and WASAPI exclusive on Windows. It embeds proven, mastering-grade resamplers (libsamplerate, r8brain, and libsoxr) so that when your songs have different sample rates, they stay clean and distortion-free.

There are no accounts, no tracking, and no ads. Just your music, your device, and clean sound.

Why Sautiplay Was Built

How a 2023 search for simple, clean Android playback turned into building a custom low-latency engine.

Sautiplay started back in 2023. At first, the goal was simple: make a basic, clean music app for Android that could deliver near bit-perfect sound without all the clutter, ads, and confusing menus found in existing players.

The real roadblock was Android itself. Real music collections are full of random sample rates — 44.1 kHz CD rips, 48 kHz video audio, 96 kHz and 192 kHz files. Android's native audio mixer forces all of them through a mediocre system resampler. Worse, phone makers bake in forced sound "enhancements" — OEM equalizers, Dolby Atmos, and DTS:X — that color and ruin the sound. Usually, the only way around that was rooting the device.

To fix this properly, I built a custom low-latency C++ engine from scratch: Sautiflow. By requesting low-latency MMAP buffers through Android's native AAudio API, Sautiplay bypasses the system mixer and skips past forced OEM sound processing on supported devices — completely root-free. And because real Android devices can reject bit-perfect or direct MMAP streams, the engine is designed to adapt gracefully instead of failing.

01 — BYPASSING OEM SOUND (ON SUPPORTED DEVICES)

  • Requests low-latency MMAP buffers via Android's native AAudio API.
  • Sends audio directly to the driver path on supported devices that allow it.
  • Steps clean around Android's shared mixer and forced OEM junk (Dolby Atmos, DTS:X, factory EQs).
  • Delivers clean audio without rooting — and handles device rejections gracefully if the HAL says no.

02 — PROPER BUILT-IN RESAMPLERS

  • Songs in real collections come in all kinds of sample rates (44.1, 48, 88.2, 96, 192 kHz).
  • Instead of trusting Android's sloppy system resampler, the engine packs top-grade resamplers: libsamplerate, r8brain, and libsoxr.
  • Local tracks get clean sinc math with zero audible distortion or muffled highs.
  • Online network streams play through FFmpeg's default resampler for fast, reliable live decoding.

03 — OPEN-SOURCE DSP ALGORITHMS

  • Instead of untested sound gimmicks, the engine relies on proven open-source DSP algorithms.
  • Uses RBJ Audio EQ Cookbook equations for parametric, shelving, and notch biquads.
  • BS2B crossfeed for fatigue-free headphone listening and partitioned FFT convolution for impulse responses.
  • Simulated and verified in MATLAB first to ensure mathematical accuracy before native C++ implementation.

04 — AUTO-RATE MATCHING & REAL-WORLD ANDROID QUIRKS

  • Song-to-DAC Rate Matching: Whenever your device or DAC supports it, Sautiplay automatically switches its sample rate to match the playing song.
  • Handling Rejections Gracefully: Android hardware varies wildly. Some phones gladly accept bit-perfect or MMAP output, while others reject it outright.
  • Smart Fallback: If a device rejects strict bit-perfect mode, Sautiplay stays locked into low-latency AAudio buffers and lets its own clean floating-point engine do the conversion.

Frequently Asked Questions

Clear answers on bit-perfect playback, Android audio routing, resampling, and DSP features.

Q: WHY DOES MY DEVICE SAY "HARDWARE DECLINED EXCLUSIVE MODE"?

Android devices have wildly different hardware abstraction layers (HALs). When you request Bit-Perfect Exclusive mode, Sautiplay asks the operating system for direct, unmixed hardware access (via AAudio MMAP).

Some internal phone DACs and vendor ROMs decline this exclusive lock. When that happens, Sautiplay doesn't crash or fail — it notifies you and falls back to low-latency shared mode, using its own clean internal floating-point engine for any required processing.

Q: HOW DOES AUTO-RATE MATCHING DIFFER FROM BIT-PERFECT?

Bit-Perfect mode attempts to lock exclusive ownership of the hardware output so no other app or system notification can mix in.

Auto Sample-Rate Match detects the exact sample rate of whatever song you're playing (44.1, 48, 96, 192 kHz) and asks the DAC to switch its internal clock to match that track. If both are on, Sautiplay manages rate-switching and exclusive access together.

Q: HOW DOES SAUTIPLAY BYPASS OEM EQUALIZERS & DOLBY ATMOS WITHOUT ROOT?

On supported Android devices, Sautiplay requests low-latency MMAP (Memory-Mapped) streams through Android's native AAudio C API.

When supported, MMAP audio writes directly to the ALSA driver and DSP hardware, completely bypassing Android's user-space AudioFlinger mixer where forced OEM sound "enhancements" (Dolby Atmos, DTS:X, and factory equalizers) are normally injected. No root required.

Q: WHICH RESAMPLER SHOULD I CHOOSE (LIBSAMPLERATE, R8BRAIN, LIBSOXR)?

All three are top-tier sinc resamplers: libsamplerate provides classic mastering-grade sinc conversion; r8brain offers ultra-clean linear/minimum phase modes with over -160 dB stopband attenuation; and libsoxr provides exceptional fidelity with very light CPU usage.

For local files, any of the three delivers mathematically transparent rate conversion with zero audible distortion or high-frequency loss.

Q: WHY DO STREAMING TRACKS USE FFMPEG'S RESAMPLER INSTEAD?

Online streams (like YouTube Music or direct URL radio) require real-time chunk demuxing, variable network bitrates, and live buffering.

FFmpeg's built-in swresample is tightly integrated into the streaming decoder pipeline to guarantee glitch-free, instantaneous live playback without buffer underruns.

Q: WHAT DOES 64-BIT FLOAT PROCESSING DO?

Standard digital audio processing uses 32-bit float (around 144–150 dB of dynamic range). When you enable 64-Bit Float Processing in Sautiplay, the entire DSP chain (equalizers, crossfeed, surround virtualizer, limiter, and volume) computes in double precision.

This yields over 320 dB of internal calculation headroom, completely eliminating accumulated rounding noise or clipping during complex multi-effect chains.

Q: CAN I IMPORT AUTOEQ PROFILES OR HEADPHONE IMPULSE RESPONSES?

Yes. Sautiplay has native support for AutoEQ (importing parametric or graphic EQ curves for thousands of headphones), Viper4Android VDC/DDC profiles, and a Convolver that can load custom stereo impulse response (.wav) files for acoustic room simulation or headphone correction.

Q: CAN I CAST TO DLNA OR USE SAUTIPLAY AS A WIRELESS RECEIVER?

Both! Sautiplay can cast out to UPnP/DLNA network speakers and smart TVs. It also includes a built-in DLNA MediaRenderer service that turns Sautiplay into a wireless receiver, letting you stream music from other phones, tablets, or computers on your local Wi-Fi network directly into Sautiplay.

Q: ARE THERE ADS, TRACKING, OR MANDATORY ACCOUNTS?

None. Sautiplay is 100% open source, privacy-focused, and offline-first. There are zero ads, zero telemetry, and no mandatory account sign-ins. All audio playback, DSP calculations, and library indexing happen entirely locally on your device.

Developer & Building Guide

One unified C++ audio core across all platforms. Here is how to configure and build for your setup.

Sautiplay is cross-platform by design. Rather than rewriting audio logic for each operating system, the entire signal path — resamplers, DSP filters, crossfeed, and decoder pipelines — lives inside a shared C++ engine (Sautiflow). Dart communicates directly with the native engine via high-performance FFI with zero overhead.

Whether you're compiling on Android with AAudio, Windows with WASAPI, Linux with ALSA/PulseAudio, or Apple platforms with CoreAudio, the underlying acoustic behavior remains identical.

To support background audio playback, system media notifications, lockscreen transport controls, and high-resolution native streaming, follow the platform configuration and setup snippets below.

SETUP 01 — ANDROID MANIFEST & BACKGROUND MEDIA SERVICE

For background playback, lockscreen media controls, and notification controls, configure android/app/src/main/AndroidManifest.xml. Note that AudioServiceActivity replaces the default FlutterActivity:

<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <!-- Permissions for background audio playback & Android 13+ notifications -->
    <uses-permission android:name="android.permission.WAKE_LOCK"/>
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK"/>
    <uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>

    <application ...>
        <!-- Main Activity must use or extend AudioServiceActivity -->
        <activity
            android:name="com.ryanheise.audioservice.AudioServiceActivity"
            android:exported="true"
            android:launchMode="singleTask">
            <intent-filter>
                <action android:name="android.intent.action.MAIN"/>
                <category android:name="android.intent.category.LAUNCHER"/>
            </intent-filter>
        </activity>

        <!-- Background Media Playback Service -->
        <service
            android:name="com.ryanheise.audioservice.AudioService"
            android:foregroundServiceType="mediaPlayback"
            android:exported="true">
            <intent-filter>
                <action android:name="android.media.browse.MediaBrowserService" />
            </intent-filter>
        </service>

        <!-- Headphone and Bluetooth hardware button receiver -->
        <receiver
            android:name="com.ryanheise.audioservice.MediaButtonReceiver"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MEDIA_BUTTON" />
            </intent-filter>
        </receiver>
    </application>
</manifest>

SETUP 02 — ANDROID NATIVE STREAMING (GRADLE)

To enable native cURL streaming for online audio and web radio in Android, configure native flags in android/gradle.properties:

MINIAUDIODART_ENABLE_CURL=ON
MINIAUDIODART_CURL_INCLUDE_DIR=/path/to/curl/include
MINIAUDIODART_CURL_LIBRARY=/path/to/libcurl.so

SETUP 03 — DART ENGINE & AUDIO SESSION INIT

Initialize the audio session for music playback and boot the native engine in your Dart entrypoint (main()):

void main() async {
  WidgetsFlutterBinding.ensureInitialized();

  // 1. Configure audio session for background music
  final session = await AudioSession.instance;
  await session.configure(
    const AudioSessionConfiguration.music(),
  );

  // 2. Initialize Sautiflow with system audio enabled
  final player = MiniAudioPlayer();
  await player.init(enableSystemAudio: true);

  runApp(const MyApp());
}

SETUP 04 — DESKTOP (WINDOWS & LINUX)

Windows: Install Visual Studio 2022 (with the Desktop development with C++ workload) and CMake.

Linux: Install build tools and audio development headers:

sudo apt install cmake ninja-build \
  libasound2-dev libpulse-dev pkg-config

SETUP 05 — APPLE (MACOS & IOS)

Requires Xcode, Command Line Tools, and CocoaPods. The C++ audio core compiles statically and binds directly to CoreAudio via FFI.

sudo gem install cocoapods
cd ios && pod install # for iOS targets

BUILDING & RUNNING WITH COMPILE-TIME STREAM URLS

Network stream endpoints are passed securely at compile time via --dart-define so credentials and URLs are never hardcoded:

# Run on connected target:
flutter run --dart-define=STREAM_URL_1="https://..." --dart-define=STREAM_URL_2="https://..."

# Build release targets:
flutter build apk --release --dart-define=STREAM_URL_1="..." --dart-define=STREAM_URL_2="..."
flutter build windows --release --dart-define=STREAM_URL_1="..." --dart-define=STREAM_URL_2="..."
flutter build linux --release --dart-define=STREAM_URL_1="..." --dart-define=STREAM_URL_2="..."
flutter build macos --release --dart-define=STREAM_URL_1="..." --dart-define=STREAM_URL_2="..."
